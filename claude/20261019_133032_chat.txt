Sorry, I used JVM jargon without explaining it. C2 isn't a capacitor here. It's the name of a part inside the Java virtual machine.

**Why something still gets compiled when the code is already in a jar**

The jar doesn't hold machine code. It holds **bytecode**, a portable format that the Pi's ARM CPU can't run directly. The JVM handles that in two ways:

1. **Interpreting:** at startup it reads the bytecode one instruction at a time and carries each one out. That works but is slow.
2. **Just-in-time (JIT) compiling:** the JVM counts how often each method runs. Once a method has run many times (that's what I meant by "hot"), it translates that method into native ARM machine code in memory so later calls are fast. This happens while the program runs, and it's never saved anywhere.

There are two of these translators:
- **C1:** fast and simple, decent code.
- **C2:** slow and thorough, best code. It's only used for the hottest methods, and it can use a lot of temporary memory while it works.

**What happened on Cleotilde**

`DenomeManager.initializePulse` runs once per pulse. After about 3 hours (roughly 120–180 pulses) the JVM decided it was hot and gave it to C2. That method is very large, and C2's temporary memory grew to about 600 MB on a Pi with 923 MB. memwatch saw that and killed the process. The flag I suggested tells the JVM never to compile that one method and just keep interpreting it. Running it interpreted once per pulse costs maybe a few milliseconds, which you wouldn't notice. The rest of the program is still compiled normally.

**What `> /dev/null 2>&1 &` does**

Every program has two output channels: **stdout** (channel 1, normal output such as `System.out.println`) and **stderr** (channel 2, error output). Read the redirect left to right:

| Part | Meaning |
|---|---|
| `> /dev/null` | Send stdout to `/dev/null`, a special file that throws away everything written to it |
| `2>&1` | Send stderr (2) to the same place as stdout (1), so it's thrown away too |
| `&` | Run the command in the background, so the script ends straight away and java keeps running |

**Why this matters for Medula**

Medula runs the script with `Utils.executeCommand`. That connects the script's stdout to a pipe and reads it until the pipe closes ("end of file"), then returns.

- **Without the redirect:** java starts in the background, but it inherits the script's stdout, so it holds Medula's pipe open. The script finishes, but the pipe never closes, because java is still holding it and runs for days. Medula sits in `readLine()` forever. That's where it has been stuck since 10:55 yesterday.
- **With the redirect:** java's output goes to `/dev/null` instead of the pipe. When the script finishes, nothing holds the pipe, so Medula gets end-of-file, returns, and carries on with its checks.

**Is anything lost?**

Almost nothing. The Hypothalamus writes its real logs through log4j to `~/Teleonome/logs/TeleonomeHypothalamus.txt`, and that isn't affected. The only things that go to stdout/stderr are stray `printStackTrace()` calls and JVM fatal-error messages. If you'd rather keep those, send them to a file instead of throwing them away:

```sh
  -jar TeleonomeHypothalamus.jar > /home/pi/Teleonome/logs/HypothalamusConsole.txt 2>&1 &
```

That fixes the hang just as well and keeps any crash messages. I'd use this version for the Hypothalamus.

The other four BG scripts (Hippocampus, Cerebellum, Heart, Webserver) need only the second change: the redirect before their final `&`.
