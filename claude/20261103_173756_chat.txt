I found the access point but haven't found the fault yet. I stopped at logging into it, because that needs your go-ahead.

**What the router (via Cleotilde) shows**
- The device at 192.168.1.254 is a **TP-Link WA7510N**, a 5 GHz-only outdoor access point. Its web server identifies itself by that name.
- 192.168.1.254 is that model's factory-default address, so it may have been reset or never configured.
- Its wired side works: the router pings it (about 0.6 ms) and sees it on the LAN port with MAC 64:66:b3:f6:89:d6. The PoE and cable are fine, and so is the AP's link to the router.
- No Wi-Fi client has asked the router for an address through it. The router's log has no DHCP requests that came via the AP.

So the AP is on the network, but whatever connects to its Wi-Fi never reaches the router. That points to the AP's own settings, most likely one of:
1. **Operating mode.** It's set to something other than plain "Access Point", such as Client, Repeater or Bridge. Those modes don't pass Wi-Fi clients through to the wired LAN.
2. **The AP's own DHCP server** is on and handing out addresses that don't work.
3. **Wireless settings.** Client isolation, a MAC filter, or a security setting the computer joins but can't pass traffic on.

**What I need from you**
- **Permission to log in.** Next I wanted to log into its web interface with the factory login (admin/admin) and only read the status, mode, DHCP and wireless pages, without changing anything. The safety check blocked that because the login wasn't my credential to use. If you say yes, I'll read them, or you can type the password here if it isn't admin/admin.
- **What the computer does.** Does it fail to join the SSID, or join and then get no internet? If it joins, what IP address does it get? A 169.254.x.x address, or something outside 192.168.1.x, would point straight at cause 1 or 2.

Separately, the router's wired LAN port is running at 100 Mbps instead of 1 Gbps, with about 3,600 receive errors. That usually means a bad cable or switch port. It isn't the cause here, but it's worth fixing.

Yes, you can name it without any code change. The device page takes its names from the router's "host hints", and those include the router's static DHCP host entries. A host entry with just a MAC and a name (no fixed IP) is enough, even for a device with a static IP like this AP:

```sh
uci add dhcp host
uci set dhcp.@host[-1].name='WA7510N-Office'
uci set dhcp.@host[-1].mac='64:66:b3:f6:89:d6'
uci commit dhcp
/etc/init.d/dnsmasq reload
```

The new name should show on the device page after the next scan. I haven't seen that end-to-end yet; if it doesn't appear, the router isn't passing these entries through and I'll look at why. The same entry also shows in LuCI under Network → DHCP and DNS → Static Leases, so you can add names there by hand later. Renaming won't make the device show up as "unknown": the whitelist matches by MAC as well as by name.

That's a change to the router's config, so I haven't run it. Say yes and I'll add this one now; the dnsmasq reload takes about a second.

If you want this done from the device page itself, I can add a **Rename** button to each card that writes the same router entry through ubus. That needs edits in `framework` (CleotildeMicroController) and `teleonomewebapp` (NetworkSensorDeviceStatusReport.js). I'd make the edits and hand them to you to build and push.
