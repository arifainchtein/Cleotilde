I read through what already exists, and a lot of this is already in place. Here's how I'd build it.

## What exists today

- **Uploads:** every `*WifiManager::uploadDataToDigitalStables()` POSTs JSON with a `totp` field to `http://devices.digitalstables.com/DeviceUploadServlet`. That servlet doesn't check codes itself. It forwards them to `ValidationServlet` at `10.192.0.2`, which looks like it sits behind your WireGuard tunnel. So the device secrets don't live on the public server, and that's worth keeping.
- **Annabelle → device over LoRa:** `DeviceCommandRecord.h` and `DeviceCommandQueue.h` already do this. Today they carry Daffodil WiFi on/off. A command goes to one serial number, Annabelle resends it until the device's own data packet shows the change, it expires after 15 minutes, and old commands can't be replayed because `senderTime` must keep increasing.
- **Gloria:** it already has `RELAY_PIN 4` and a LoRa receiver for `GloriaCommandData` (fieldId, code, `char[64]`). It checks the code, but nothing acts on the command yet. Right now the relay just toggles on a test timer at seconds 40 and 50.

## The main constraint: the server can't send to a device

Your customers' devices are behind their home routers. devices.digitalstables.com has no way to reach in, so "the server sends a message to Annabelle" has to become **the device asks the server**. There are two ways to do that:

1. **Short polling (start here):** the device calls `GET /DeviceCommandServlet?serial=…` every 10–15 s and gets back "nothing" or a command. It's simple, works with your Tomcat setup, and the delay is a few seconds.
2. **A persistent connection (later):** the device keeps an MQTT-over-TLS connection open and commands arrive immediately. You already run moquette, so this is familiar, but it's more to operate.

I'd also have the normal upload response carry any pending command, so it gets through even when polling is slow.

## The two delivery paths

**Gloria has internet itself:**
customer → login + TOTP → server stores the command → Gloria polls and gets it → **Gloria checks it** → relay on → Gloria's next upload shows the pump running → the page shows "confirmed".

**Gloria only has LoRa:**
same up to the server → **Annabelle** polls for every serial she has heard → puts it in `DeviceCommandQueue` → LoRa → **Gloria checks it** → relay on → Gloria's LoRa data packet shows the pump running → Annabelle marks it done and reports back → the page shows "confirmed".

Annabelle only relays the command. Gloria does the checking, so a compromised or spoofed Annabelle can't invent commands.

## Security: what has to change

1. **Sign the command, don't just stamp it with a code.** `DeviceCommandRecord` carries a TOTP for `senderTime`, but that code doesn't cover the command bytes. Anyone near the farm can record a LoRa packet, and someone who can intercept it could change "on 5 min" to "on 255 min" and keep the valid code. For a pump, use an **HMAC-SHA256 over (serial, command, duration, senderTime)** with the device's secret, truncated to 8–16 bytes so it fits LoRa. ESP32's mbedtls does this cheaply. Keep the existing "senderTime must increase and be close to my clock" rule.
2. **The signature should come from the secret holder (10.192.0.2), not the public server.** The public server says "user X, who owns serial Y, asked for pump-on 20 min". The validation machine checks that ownership and returns the signed command. The keys never touch the internet-facing machine.
3. **Signing matters more than encrypting.** "Pump on" isn't secret. What matters is that nobody can forge or alter it, and the HMAC covers that. You can add encryption on top, but it's optional.
4. **Use HTTPS for the polling and upload links.** Today they're plain `http://`. That's tolerable for sensor readings but not for a control channel. `WiFiClientSecure` with a pinned root CA works on ESP32.
5. **Customer side:** login + their own authenticator TOTP (a different secret from the device's), a table of which user owns which device, and a log of every command.

## Pump safety, which matters more than the crypto

- Every command has a **duration** ("on for 20 min"), never a bare toggle. Gloria turns the pump off by herself when the time is up, and after a reboot the pump is always off.
- Gloria enforces her own **maximum run time** and **dry-run cutoff** from her tank and flow sensors, whatever the command says.
- If someone switches it off at the device, that wins over a remote command.
- The page shows the real state in steps: *queued → delivered → confirmed by device data* (or *expired*). It never shows "on" just because a button was clicked.

| DigitalStablesEsp32Lib | Shared signed remote-command record + HMAC check, a polling function in `WifiManager`, HTTPS |

## Why it works on any stock router

Any commercial router lets devices inside the house open connections to the internet and lets the replies come back. That's how phones and smart TVs work. Nothing is opened from the outside:

- Gloria or Annabelle opens a connection to `devices.digitalstables.com:443` and asks "anything for me?"
- The server answers on that same connection.
- The farmer's router sees ordinary outgoing web traffic, the same as a browser.

So we don't need a fixed IP, port forwarding, dynamic DNS or a VPN on the customer side. It also works when the ISP shares one public IP among many customers (CGNAT), which is common on rural and 4G modems. In that case, port forwarding is impossible anyway.

WireGuard is still right for your factory, where you want to reach your own machines from outside. Customers never need it.

## What the farmer actually does

1. Plugs in Annabelle (or Gloria) and joins it to their WiFi, using the setup page the devices already have.
2. Creates an account on devices.digitalstables.com, scans the TOTP QR code with their phone, and claims the device. For example, they type the serial number plus a one-time code shown on Annabelle's screen or page, which proves they physically have the device.
3. From then on, they log in from town and press "Pump on 20 min".

## Details the firmware has to handle

- **Port 443 only.** Some locked-down or cellular connections block unusual ports. HTTPS on 443 always gets through, so I'd use HTTPS polling first. If we later use MQTT, it should run over 443 too, not 1883 or 8883.
- **Connections that die without notice.** Cheap routers and 4G modems silently drop idle connections after a few minutes. Short polling avoids this. A long-lived connection would need a keepalive every 30–60 s.
- **Internet outages.** Rural lines drop often. A queued command expires (like the existing 15-minute timeout) rather than running hours late. The page shows "not delivered" honestly, and the pump's built-in time limit means a lost "off" message can't leave it running.
- **Router reboots and new IPs.** The device just reconnects. Nothing depends on the farm's address.

None of this changes the plan from my last message: polling from the device, signed commands, Annabelle relaying over LoRa, and the pump safety limits. I still need your answers on Gloria's power (is she always listening?) and what 10.192.0.2 is before we pin down the signing.

I've added this to the design doc as §5.4. The PDF is regenerated and has replaced the copy on Continuity, so the link in today's item opens the new version.

**The rule:** both paths keep uploading, and the server keeps one copy. Having Annabelle skip devices that have WiFi would lose data on exactly the days the device's own upload fails, which is when the second path matters most. The extra upload is a few hundred bytes per reading.

How the doc says to do it:
1. **A reading is identified by its serial number plus `secondsTime`**, the device's own clock time when it took the sample. Each device must stamp a reading once and put that same time in both the WiFi upload and the LoRa packet. If either path stamps its own send time, the two copies won't match and the duplicate gets through.
2. **Server side:** a unique index on `devicedata(serialnumber, secondsTime)`, and duplicates are ignored on insert. Today `insertDeviceData()` does a plain insert, so duplicates already get stored. A duplicate still gets the answer `Ok`, so neither sender keeps retrying it. Old duplicate rows need a one-off clean-up before the index can be created.
3. **The server records how each copy arrived:** directly, or via which Annabelle, with the LoRa signal strength. The page can then show "heard directly and by Annabelle", which helps spot a device whose WiFi is failing.
4. **A relayed reading is checked against Annabelle's own code**, accepted only for devices on her farm. I found a bug here: `generateDigitalStablesData()` writes `sentBy` as the device's own serial, even though Annabelle had just set it to hers. So today the server can't tell a relayed reading from a direct one.

The same idea applies to pump commands. If Chinampa gets the same command over WiFi and through Annabelle, it acts on the first copy and quietly ignores the second, which has the same `commandId`.

I added this to phase 0 and to Annabelle's changes, plus a new open question 9 in §11. The question is whether every device's firmware really stamps a reading once; that needs checking per device.
